## 1. 저장할 수 있는 데이터에도 기준이 필요하다

데이터베이스에 값이 저장되었다고 해서 그 값이 모두 올바르다고 볼 수는 없다.

상품 가격이나 주문 수량이 음수로 들어가거나, 주문 정보가 실제로 존재하지 않는 고객을 가리킨다면 이를 이용한 조회 결과도 믿기 어려워진다. 잘못된 데이터는 보고서의 계산 결과를 왜곡하거나 프로그램이 예상하지 못한 동작을 일으키는 원인이 될 수 있다.

이런 문제를 줄이기 위해서는 데이터가 일정한 규칙을 지키도록 해야 한다. **데이터 무결성(Data Integrity)** 은 저장된 데이터의 정확성, 일관성, 유효성을 유지하는 것을 의미한다.

프로그램에서 입력값을 검사할 수도 있지만, 데이터가 변경되는 경로는 프로그램 하나로 한정되지 않는다. 다른 프로그램이나 데이터베이스에 직접 접근하는 작업도 있기 때문에, 데이터베이스 자체에도 규칙을 정할 필요가 있다.

이때 테이블에 설정하는 규칙이 **제약 조건(Constraint)** 이다. 제약 조건에 어긋나는 데이터 변경은 데이터베이스가 허용하지 않는다.

---

## 2. 값이 비어 있거나 중복되는 상황을 제한하기

테이블을 만들 때 자주 사용하는 제약 조건은 다음과 같다.

### NOT NULL: 반드시 입력되어야 하는 값

`NOT NULL`이 지정된 컬럼에는 `NULL`을 저장할 수 없다.

예를 들어 이메일이 필수 정보라면 해당 컬럼에 `NOT NULL`을 설정하여 값이 없는 상태로 저장되지 않도록 할 수 있다.

### UNIQUE: 같은 값을 두 번 저장하지 않기

`UNIQUE`는 지정한 컬럼의 값이 다른 행과 중복되지 않도록 한다.

회원 이메일처럼 동일한 값이 여러 행에 등록되면 안 되는 경우에 사용할 수 있다. 이미 저장된 이메일을 다시 입력하면 중복으로 인해 해당 작업이 거부된다.

### PRIMARY KEY: 각 행을 구분하는 기준

`PRIMARY KEY`는 테이블의 행을 식별하는 대표 키다. 기본 키 값은 중복될 수 없으며 `NULL`도 허용하지 않는다.

테이블에는 기본 키 제약 조건을 하나만 지정할 수 있다. MySQL에서는 기본 키를 설정하면 이를 위한 인덱스도 자동으로 생성된다.

### DEFAULT: 값을 생략했을 때 사용할 값

`DEFAULT`는 데이터를 추가하면서 특정 컬럼의 값을 지정하지 않았을 때 사용할 기본값을 정한다.

가령 주문 상태의 기본값을 `PENDING`으로 설정하면, 주문 등록 시 상태를 생략한 경우 해당 값이 사용된다.

`DEFAULT`는 잘못된 값을 직접 검사해서 거부하는 제약 조건이라기보다는, 입력을 생략했을 때 적용할 값을 미리 마련하는 기능으로 이해했다.

## 3. 테이블 사이의 연결이 끊어지지 않도록 하기

테이블을 나누어 저장할 때는 각 테이블의 값뿐 아니라 **테이블 간의 참조 관계**도 올바르게 유지해야 한다. 이를 참조 무결성이라고 한다.

예를 들어 `orders.user_id`가 `users.user_id`를 참조한다면, 주문에 기록된 고객 번호는 실제 고객 테이블에 존재하는 값이어야 한다.

이 관계를 데이터베이스에서 검사하도록 설정하는 것이 **외래 키(Foreign Key)** 제약 조건이다.

외래 키는 크게 두 상황에서 영향을 준다.

- **주문 추가·수정:** 부모 테이블에 없는 고객 번호를 참조하는 값으로 입력하거나 변경하는 작업을 막는다.
- **고객 삭제·수정:** 다른 테이블에서 참조 중인 고객의 키를 삭제하거나 변경하려는 경우, 설정된 참조 동작 규칙에 따라 처리한다.

예를 들어 고객의 주문 내역이 남아 있는데 해당 고객을 삭제하면 주문이 존재하지 않는 고객을 가리키게 될 수 있다. 외래 키에 별도의 연쇄 처리 옵션을 두지 않았다면 이러한 삭제는 제한된다.

참조 중인 고객을 삭제해야 하고 삭제 제한이 적용되어 있다면, 관련 주문 데이터를 먼저 삭제한 뒤 고객을 삭제하는 순서로 처리할 수 있다.

---

## 4. 참조 대상이 변경될 때의 처리 방식

외래 키에는 부모 테이블의 데이터가 바뀌었을 때 자식 테이블을 어떻게 처리할지 정하는 옵션이 있다.

`ON DELETE`는 부모 행의 삭제에, `ON UPDATE`는 참조하는 키 값의 변경에 관한 설정이다.

| 옵션 | 처리 방식 |
| --- | --- |
| `RESTRICT` | 해당 값을 참조하는 자식 행이 있으면 부모 행의 삭제 또는 키 변경을 제한한다. |
| `CASCADE` | 부모 행이 삭제되면 연결된 자식 행도 삭제하고, 참조 키가 변경되면 자식의 외래 키 값도 함께 변경한다. |
| `SET NULL` | 부모 행이 삭제되거나 참조 키가 변경될 때 자식의 외래 키 값을 `NULL`로 바꾼다. |

즉, 외래 키가 있다는 사실만으로 부모 행이 항상 삭제되지 않는 것은 아니다. **어떤 참조 동작을 설정했는지**에 따라 결과가 달라진다.

## 5. 숫자나 값의 허용 범위를 정하기

`NOT NULL`이나 `UNIQUE`만으로는 값이 업무상 적절한지 모두 확인할 수 없다.

예를 들어 상품 가격에 값이 존재하고 중복되지 않더라도, 그 가격이 음수라면 정상적인 상품 데이터로 보기 어렵다.

이처럼 입력 가능한 값에 조건을 붙일 때 **`CHECK`** 제약 조건을 사용할 수 있다. 데이터를 추가하거나 수정할 때 조건식을 검사하며, 조건을 만족하지 않는 값은 거부한다.

```sql
price INT NOT NULL CHECK (price >= 0)
```

위 정의에서는 상품 가격에 `NULL`을 넣을 수 없고, 0보다 작은 값도 저장할 수 없다.

이번 학습에서 다룬 조건은 다음과 같다.

- 상품 가격은 0 이상
- 재고 수량은 0 이상
- 할인율은 0부터 100까지

제약 조건을 직접 구분할 이름이 필요하다면 `CONSTRAINT`로 이름을 붙일 수도 있다.

```sql
CONSTRAINT products_chk_price CHECK (price >= 0)
```

---

## 6. 정리

이번 내용은 데이터가 저장된 뒤에 오류를 찾는 것뿐 아니라, **잘못된 데이터가 저장되지 않도록 데이터베이스에 규칙을 두는 방법**에 관한 것이다.

`NOT NULL`, `UNIQUE`, `PRIMARY KEY`는 값의 필수 여부와 중복 및 식별 기준을 다루고, `DEFAULT`는 생략된 값에 적용할 기본값을 정한다. `FOREIGN KEY`는 테이블 간 참조 관계를 유지하고, `CHECK`는 데이터가 만족해야 할 조건을 검사한다.

각 제약 조건의 역할은 다르지만, 공통적으로 데이터베이스가 정해진 기준에 맞는 데이터를 관리하도록 한다는 점으로 이해했다.
