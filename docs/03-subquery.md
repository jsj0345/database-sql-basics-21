# 서브쿼리

## 1. 다른 조회의 결과를 조건으로 사용하기

SQL을 작성하다 보면 바로 조건을 정하기 어려운 경우가 있다.

예를 들어 전체 상품의 평균 가격보다 비싼 상품을 찾으려면 먼저 평균 가격을 알아야 한다.

이 값을 따로 구해서 다시 조건에 넣을 수도 있지만, 필요한 값을 구하는 조회 자체를 다른 SQL 안에 넣을 수도 있다.

```sql
SELECT name, price
FROM products
WHERE price > (
    SELECT AVG(price)
    FROM products
);
```

내가 이해한 서브쿼리는 **먼저 필요한 값을 조회하고, 그 결과를 다른 조회의 조건으로 사용하는 방법**이다.

---

## 2. 안쪽 조회와 바깥쪽 조회를 나누어 보기

서브쿼리는 하나의 SQL 안에 또 다른 `SELECT`문이 들어 있는 구조다.

```text
안쪽 SELECT
→ 비교에 필요한 값을 구함

바깥쪽 SELECT
→ 그 값을 이용해 최종 데이터를 조회
```

따라서 서브쿼리를 볼 때는 먼저 괄호 안쪽에서 어떤 값을 구하는지 확인하는 것이 이해하기 쉽다.

---

## 3. 결과가 하나라면 하나의 값처럼 비교한다

서브쿼리 결과가 **한 행, 한 컬럼**이라면 하나의 값처럼 사용할 수 있다.

이런 형태를 스칼라 서브쿼리라고 한다.

하나의 값이 나오기 때문에 다음과 같은 비교 연산자와 함께 사용할 수 있다.

```text
=
>
<
>=
<=
<>
```

예를 들어 특정 주문을 한 고객의 주소를 구한 뒤 같은 주소를 가진 고객을 찾는 식으로 사용할 수 있다.

핵심은 **서브쿼리가 하나의 값을 반환한다는 점**이다.

---

## 4. 하나의 값과 비교할 때는 결과도 하나여야 한다

`=`처럼 하나의 값과 비교하는 연산자를 사용한다면 서브쿼리 역시 하나의 행을 반환해야 한다.

```text
컬럼 = (서브쿼리)
```

그런데 서브쿼리에서 여러 행이 반환되면 어느 값과 비교해야 하는지 정할 수 없다.

이 경우 다음과 같은 오류가 발생할 수 있다.

```text
Error Code: 1242. Subquery returns more than 1 row
```

따라서 서브쿼리를 사용할 때는 **안쪽 조회가 몇 개의 행을 반환하는지 확인해야 한다.**

---

## 5. 여러 행을 반환하는 서브쿼리

서브쿼리의 결과가 항상 하나일 필요는 없다.

예를 들어 특정 카테고리에 속한 상품 ID를 조회하면 여러 상품이 존재할 수 있으므로 여러 행이 반환될 수 있다.

이처럼 서브쿼리에서 여러 값이 나오는 경우에는 여러 값을 처리할 수 있는 연산자가 필요하다.

이번 내용에서는 다음을 사용했다.

```text
IN
ANY
ALL
```

---

## 6. IN으로 여러 값 중 일치하는 값 찾기

`IN`은 여러 값 중 현재 값과 같은 값이 존재하는지를 확인할 때 사용할 수 있다.

```sql
SELECT *
FROM orders
WHERE product_id IN (
    SELECT product_id
    FROM products
    WHERE category = '전자기기'
);
```

안쪽 조회에서는 여러 상품 ID가 반환될 수 있다.

바깥쪽 조회에서는 각 주문의 `product_id`가 그 목록 안에 포함되는지를 확인한다.

```text
서브쿼리
→ 여러 값 조회

IN
→ 그중 일치하는 값이 있는지 확인
```

---

## 7. ANY와 ALL로 여러 값 비교하기

`ANY`와 `ALL`은 여러 값을 비교 연산자와 함께 사용할 때 사용한다.

| 조건 | 의미 |
| --- | --- |
| `> ANY` | 결과 중 하나보다 크면 만족 |
| `> ALL` | 결과의 모든 값보다 커야 만족 |
| `< ANY` | 결과 중 하나보다 작으면 만족 |
| `< ALL` | 결과의 모든 값보다 작아야 만족 |
| `= ANY` | `IN`과 같은 의미 |

예를 들어 비교 대상이 다음과 같다면

```text
100, 200, 300
```

`> ANY`는 하나보다만 커도 되기 때문에 최소값인 `100`보다 크면 만족한다.

반대로 `> ALL`은 모든 값보다 커야 하므로 최대값인 `300`보다 커야 한다.

```text
ANY
→ 여러 값 중 하나라도 조건을 만족

ALL
→ 여러 값 전체가 조건을 만족
```

---

## 8. ANY와 ALL을 집계값으로 바꾸어 표현하기

이번 내용에서는 `ANY`, `ALL` 조건을 `MIN()`, `MAX()`를 사용한 형태로 바꿀 수도 있었다.

```text
> ANY
→ 최소값보다 큰지 비교

> ALL
→ 최대값보다 큰지 비교
```

예를 들어 `> ANY` 조건은 다음과 같이 표현할 수 있다.

```sql
WHERE price > (
    SELECT MIN(price)
    FROM products
    WHERE category = '전자기기'
)
```

`> ALL`은 같은 방식으로 `MAX()`를 이용할 수 있다.

---

## 9. 여러 컬럼을 하나의 조건으로 비교하기

서브쿼리는 하나의 컬럼만 반환하는 것이 아니라 여러 컬럼을 함께 반환할 수도 있다.

예를 들어 주문의 `user_id`와 `status`를 함께 비교해야 한다면 다음처럼 두 컬럼을 묶어서 사용할 수 있다.

```sql
WHERE (user_id, status) = (
    SELECT user_id, status
    FROM orders
    WHERE order_id = 3
)
```

이 경우 두 값 중 하나만 비교하는 것이 아니라

```text
(user_id, status)
```

라는 값의 조합을 기준으로 비교한다.

---

## 10. 여러 컬럼을 비교할 때도 결과 행 수를 확인한다

다중 컬럼 서브쿼리에서도 `=`을 사용한다면 서브쿼리의 결과는 하나의 행이어야 한다.

```text
(user_id, status) = (서브쿼리)
```

서브쿼리에서 여러 행이 반환될 수 있다면 `=` 대신 `IN`을 사용할 수 있다.

```text
(컬럼1, 컬럼2) IN (서브쿼리)
```

이 경우 바깥쪽의 컬럼 값 조합이 서브쿼리가 반환한 여러 결과 중 하나와 일치하는지를 확인한다.

---

## 11. 여러 컬럼의 조합 중 일치하는 결과 찾기

이번 내용에서는 고객별 가장 빠른 주문을 찾을 때도 여러 컬럼을 함께 비교했다.

핵심 조건만 보면 다음과 같다.

```sql
WHERE (o.user_id, o.order_date) IN (
    SELECT user_id, MIN(order_date)
    FROM orders
    GROUP BY user_id
);
```

안쪽 조회에서는 고객별로

```text
사용자 ID + 가장 빠른 주문 날짜
```

의 조합을 만든다.

바깥쪽에서는 각 주문의 `(user_id, order_date)`가 그 결과 중 하나와 일치하는지를 확인한다.

즉 여러 컬럼을 함께 묶고, 그 값의 조합을 기준으로 여러 결과와 비교할 수도 있다.

--- 

## 12. 바깥쪽 행을 기준으로 다시 계산하기

앞에서 본 서브쿼리는 안쪽 조회가 먼저 값을 만든 뒤, 바깥쪽 조회가 그 결과를 사용하는 형태였다.

하지만 비교 기준이 고정되어 있지 않고 **현재 조회 중인 행에 따라 달라지는 경우**도 있다.

예를 들어 상품마다 자신의 카테고리 평균 가격과 비교해야 한다면, 서브쿼리는 바깥쪽 쿼리가 현재 어떤 카테고리를 보고 있는지 알아야 한다.

이처럼 서브쿼리에서 메인쿼리의 값을 참조하는 구조를 **상관 서브쿼리**라고 한다.

```text
메인쿼리의 한 행 확인
→ 그 행의 값을 서브쿼리에서 사용
→ 결과를 이용해 조건 판단
→ 다음 행에서 같은 과정 반복
```

일반적인 서브쿼리와의 차이는 **서브쿼리가 바깥쪽 쿼리의 값에 의존하는지**에 있다.

```text
일반 서브쿼리
→ 안쪽 조회 결과를 바깥쪽 조회에서 사용

상관 서브쿼리
→ 바깥쪽의 현재 행 값을 안쪽 조회에서도 참조
```

상품별로 같은 카테고리의 평균 가격과 비교하는 핵심 구조만 보면 다음과 같다.

```sql
WHERE price >= (
    SELECT AVG(price)
    FROM products p2
    WHERE p2.category = p1.category
)
```

여기서 `p1.category`는 메인쿼리가 현재 보고 있는 상품의 카테고리다.

서브쿼리는 이 값을 기준으로 같은 카테고리의 상품만 골라 평균을 계산하고, 메인쿼리는 현재 상품의 가격과 그 결과를 비교한다.

즉 상관 서브쿼리를 볼 때는 **서브쿼리 안에서 바깥쪽 테이블의 별칭을 참조하고 있는지** 확인하면 구조를 이해하기 쉽다.

## 13. 값의 목록보다 존재 여부가 중요할 때

주문 내역이 있는 상품만 찾는다면 먼저 주문된 `product_id` 목록을 구한 뒤 `IN`으로 비교할 수 있다.

```sql
WHERE product_id IN (
    SELECT DISTINCT product_id
    FROM orders
)
```

이 방식은 서브쿼리에서 주문된 상품 ID 목록을 만들고, 메인쿼리의 상품 ID가 그 안에 포함되는지를 확인한다.

반대로 필요한 것이 실제 값의 목록이 아니라 **조건에 맞는 행이 존재하는지 여부**라면 `EXISTS`를 사용할 수 있다.

```sql
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.product_id = p.product_id
)
```

`EXISTS`는 서브쿼리에서 어떤 값을 조회했는지보다 **결과 행이 존재하는지**를 기준으로 판단한다.

```text
결과 행이 있음
→ TRUE

결과 행이 없음
→ FALSE
```

위 조건에서는 서브쿼리가 메인쿼리의 `p.product_id`를 참조하므로 상관 서브쿼리 형태가 된다.

`SELECT 1`을 사용하는 이유도 실제 조회값이 목적이 아니라 행의 존재 여부만 확인하기 때문이다.

이번 내용에서 정리한 `IN`과 `EXISTS`의 흐름은 다음처럼 구분할 수 있다.

```text
IN
→ 서브쿼리에서 비교할 값의 목록을 구함
→ 메인쿼리에서 목록과 비교

EXISTS
→ 메인쿼리의 현재 행을 기준으로 서브쿼리 확인
→ 조건에 맞는 행의 존재 여부를 판단
```

상관 서브쿼리는 메인쿼리의 행을 처리하면서 서브쿼리가 반복해서 실행될 수 있으므로 데이터가 많을 때는 성능도 함께 고려해야 한다.

같은 결과를 `JOIN`으로 표현할 수 있는 경우도 있으며, 반대로 존재 여부만 확인하는 조건에서는 `EXISTS`를 사용할 수 있다.

따라서 상관 서브쿼리는 **현재 행의 값이 안쪽 조회에 필요한지**, 그리고 **실제 값이 필요한지 존재 여부만 필요한지**를 구분해서 보는 것이 핵심이다.
