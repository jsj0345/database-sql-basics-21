# VIEW

## 1. 반복해서 사용하는 조회문을 관리하려면

여러 테이블을 조인하고 집계하는 SQL은 필요한 결과를 한 번에 보여줄 수 있지만, 동일한 조회가 자주 필요하다면 관리할 내용도 많아진다.

이번 학습에서는 `orders`와 `products`를 연결한 뒤 상품 카테고리별 주문 건수와 상태별 건수를 계산하는 조회를 사용했다. 이런 SQL을 여러 곳에서 각각 보관하면 같은 조회 조건을 반복해서 작성해야 하고, 집계 기준이 바뀔 때도 수정할 곳이 늘어난다.

또한 보고서 결과만 필요한 사용자에게 원본 테이블의 모든 정보를 보여줄 필요는 없다.

**조회문을 반복해서 작성하는 대신, 필요한 결과를 하나의 이름으로 사용할 수 있는 방법**이 뷰(`VIEW`)다.

---

## 2. 데이터 대신 조회 정의를 보관한다

뷰는 조회 결과를 별도로 저장하는 테이블이 아니라, `SELECT`문을 이름과 함께 등록하여 사용하는 데이터베이스 객체다.

뷰를 조회할 때는 저장된 조회 정의를 바탕으로 결과를 얻는다. 따라서 사용자는 원래의 긴 SQL을 직접 입력하지 않고도, 뷰를 테이블처럼 `SELECT`문에 사용할 수 있다.

```text
조회에 필요한 SELECT문 작성
→ VIEW 이름으로 등록
→ 이후 VIEW 이름을 이용해 결과 조회
```

핵심은 **조회 결과를 새로운 테이블에 복사하는 것이 아니라, 결과를 만드는 SQL을 재사용한다는 점**이다.

---

## 3. 뷰를 통해 줄일 수 있는 불편함

이번 내용에서 뷰의 용도는 크게 세 가지로 나눌 수 있었다.

- **조회 재사용:** 복잡한 SQL을 이용해야 할 때 매번 같은 문장을 다시 작성하지 않아도 된다.
- **노출 범위 제한:** 원본 테이블에 대한 직접 접근을 허용하지 않고, 뷰를 통해 필요한 행이나 컬럼만 제공할 수 있다.
- **변경 대응:** 원본 테이블의 일부 구조가 달라져도 뷰 정의를 조정하여 기존 조회 방식이 유지되도록 할 수 있는 경우가 있다.

즉, 뷰를 사용하면 조회를 작성하는 쪽과 실제 데이터를 관리하는 쪽 사이에 하나의 조회 정의를 둘 수 있다.

---

## 4. SELECT문에 이름 붙여 등록하기

뷰를 만드는 명령어는 `CREATE VIEW`다. 작성한 `SELECT`문을 어떤 이름으로 조회할지 지정한다.

```sql
CREATE VIEW 뷰이름 AS
SELECT ...;
```

원본 실습에서는 상품 카테고리별 주문 현황을 계산하는 `JOIN`, `GROUP BY`, `SUM(CASE ...)` 조회를 하나의 뷰로 등록했다.

이름에 `v_` 등의 접두사를 붙여 일반 테이블과 구분할 수도 있다. 뷰가 만들어졌다고 해서 원본 주문이나 상품 데이터를 별도로 복사해 저장하는 것은 아니다.

---

## 5. 등록한 뷰에서 결과 가져오기

생성한 뷰는 `FROM` 뒤에 이름을 적어 조회할 수 있다.

```sql
SELECT *
FROM v_category_order_status;
```

위 쿼리는 실습에서 등록한 카테고리별 주문 집계 결과를 확인하는 용도다.

처음에는 여러 테이블을 연결하고 조건별 건수를 계산하는 내용이 필요했지만, 뷰를 만든 뒤에는 **해당 조회를 어떤 이름으로 등록했는지만 알면 같은 형태의 결과를 요청할 수 있다.**

---

## 6. 저장된 조회 내용을 변경하기

기존 뷰의 조회 항목이나 계산 방식이 달라져야 한다면 `ALTER VIEW`로 정의를 변경할 수 있다.

```sql
ALTER VIEW 뷰이름 AS
SELECT ...;
```

이번 실습에서는 카테고리별 주문 건수와 상태별 건수에 더해, 상품 가격과 주문 수량을 이용한 매출 합계를 조회 항목에 포함했다.

기존 뷰를 사용하는 쿼리 자체를 새로 작성하는 대신, **뷰 내부의 SELECT 정의를 바꾸어 조회 결과에 새로운 컬럼을 추가한 것**이다.

---

## 7. 같은 조회를 여러 곳에서 사용하기

여러 테이블을 연결하거나 조건을 조합한 SQL을 반복해서 작성해야 한다면, 필요한 조회를 뷰로 등록해 사용할 수 있다.

사용하는 쪽에서는 복잡한 계산 과정을 직접 작성하지 않고 뷰의 이름으로 결과를 요청한다. 개발하는 쪽에서도 여러 곳에 같은 SQL을 따로 관리하는 대신, **공통으로 사용하는 조회 정의를 한곳에서 변경할 수 있다.**

따라서 이번 내용에서는 뷰의 장점을 쿼리 길이를 줄이는 것뿐 아니라, 반복되는 조회 로직을 관리하는 방법으로 이해했다.

---

## 8. 보여줄 데이터를 구분해서 제공하기

뷰를 통해 원본 테이블의 모든 정보를 조회하도록 하지 않고, 필요한 범위만 제공할 수도 있다.

- **컬럼 제한:** 직원 정보 중 연봉이나 개인정보에 해당하는 항목을 제외한 결과를 제공한다.
- **행 제한:** 주문 내역 중 특정 캠페인과 관련된 데이터만 조회하도록 구성한다.

이처럼 뷰에 필요한 내용만 정의하고 해당 뷰에 대한 조회 권한을 부여하면, 원본 테이블을 직접 조회하지 않고도 정해진 데이터에 접근할 수 있다.

---

## 9. 테이블이 바뀌어도 조회 형태를 유지하는 경우

원본 테이블의 구성과 프로그램이 사용하는 조회 결과를 반드시 같은 형태로 둘 필요는 없다.

테이블이 나뉘거나 컬럼 이름이 변경되더라도 **뷰에서 이전과 같은 조회 구조를 제공할 수 있다면**, 프로그램은 기존에 사용하던 형태로 결과를 받아볼 수 있다.

즉 뷰는 실제 테이블의 구조와 데이터를 사용하는 쪽 사이에서 차이를 조정하는 역할도 할 수 있다. 원본 테이블의 구조가 변경되더라도 뷰를 통해 이전과 같은 조회 결과를 제공하면, 프로그램에서 기존 조회 방식을 유지할 수 있다.

---

## 10. 짧은 조회문이라고 실행도 가벼운 것은 아니다

뷰를 사용하는 SQL은 간단해 보여도, 실제로는 뷰에 등록된 복잡한 조회를 바탕으로 결과가 만들어진다.

따라서 **작성된 SQL이 짧다는 이유만으로 처리 부담이 작다고 판단할 수는 없다.** 뷰의 구성이 복잡하면 데이터베이스가 효율적인 실행 계획을 정하는 데 제약이 생길 수 있다.

특히 다른 뷰를 다시 참조하는 구조를 여러 겹으로 만들면 성능 문제가 생길 수 있으므로 주의해야 한다.

---

## 11. 조회와 데이터 변경은 구분해서 생각하기

뷰를 `SELECT`에서 테이블처럼 사용한다고 해서 데이터 변경까지 항상 가능한 것은 아니다.

`JOIN`, 집계 함수, `GROUP BY`, `DISTINCT` 등을 사용하는 뷰는 구조에 따라 데이터 변경이 제한될 수 있다. 특히 집계 결과를 나타내는 뷰는 일반 테이블처럼 데이터를 추가하거나 수정할 수 없다. 뷰에서 나타난 결과 한 행이 원본 데이터의 어떤 변경으로 이어져야 하는지 정하기 어려울 수 있기 때문이다.

반면 하나의 기본 테이블을 사용하고 그 테이블의 컬럼을 직접 조회하는 형태라면 데이터를 추가하거나 수정할 수 있는 경우가 있다. 이때 변경되는 대상은 뷰에 따로 저장된 값이 아니라 **원본 테이블의 데이터**다.

이번 내용을 통해 뷰는 조회에 편리하지만, 모든 뷰가 일반 테이블과 같은 방식으로 데이터를 변경할 수 있는 것은 아니라는 점을 구분했다.
